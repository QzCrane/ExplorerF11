# ExplorerF11 1.0.4

A pass over every behaviour, speed and memory alike. The tray, the menu, the
report and the CLI print the same bytes as 1.0.3; what changes is what they cost.
One defect was found by the pass and is fixed: `--no-initial` never took effect.
The single-file executable is 420,864 bytes (411 KiB), 41 KiB larger than 1.0.3
because its small icon sizes are now stored uncompressed, so loading them no
longer pulls an imaging decoder into the process.

## What you get

One 64-bit Windows executable — no installer, no runtime, no external files.
Put `ExplorerF11-1.0.4-win64.exe` anywhere and run it. Built with MinGW-w64
GCC 16.1.0 through `make -B` on the release machine; MSVC builds the same
sources in CI with `/std:c++latest`.

## Performance

Every figure is from `make bench` and the probe tools in `tools/`, on a normal
desktop; the method and the rejected alternatives are in
[docs/PERFORMANCE.md](https://github.com/QzCrane/ExplorerF11/blob/main/docs/PERFORMANCE.md).

- **The marked-window set is maintained instead of rediscovered.** The count on
  the tooltip used to walk every top-level window and read our property on each
  one — 0.26 ms on a 360-window desktop, 88% of it the property read. `Mark()`
  is the only writer of that property, so it now reports the handle; every read
  re-validates the recorded handles with `IsWindow` + `GetPropW`, and the first
  read seeds from one full walk so marks from an earlier run are still counted.
  Same answer, **0.26 ms → 0.002 ms (147×)** measured back to back in one
  process. A full report build fell **1.52 ms → 1.03 ms (−32%)**. The set cannot
  drift: every way it could be wrong is closed and checked against a fresh walk
  in seven live states by `tools/verify_marks.cpp`.
- **The tray is pushed only when its surface changes.** Most state changes end
  in the same two lines of text — a second apply-all, a recovery timer that finds
  nothing, a hover whose count has not moved. `PushTraySurface()` compares the
  freshly built tip and icon with what the shell was last told and returns before
  the IPC when they match; a real change still pushes. The comparison is against
  live state, never a cache, so a stale surface corrects itself on the next
  event. Hover went from a window walk plus a **1.2–1.7 ms** round trip to
  **~2 µs and no IPC**.
- **`UserAssist` is searched with a rotated needle.** ROT13 commutes with case
  folding, so searching the decoded string for the name is exactly searching the
  raw string for the rotated name. One rotation per scan replaces a decode per
  value: **88 µs → 50 µs (−43%)** over the 309 names on this machine.
  `StrStrIW`, the obvious alternative, measured **19× slower**.
- **The tray menu asks presence, not contents.** The count on the label ran the
  full eleven-probe scan; it now uses the same probe rules with a stop-at-first-
  hit depth. **1.29 ms → 1.00 ms** per menu open, and the menu count still equals
  the report count by construction.
- **An event burst rebuilds an open report once.** Ten windows opening in a row
  used to re-probe eleven locations ten times to paint one final state. The
  report is marked dirty and rebuilt once, still from live state.
- **“Copy all” copies what is on screen** instead of rebuilding it.

Speed has a wall that is not code: `--status` costs 12.7 ms, of which 85% is
Windows creating a process. Nothing here changed that, and no number above
depends on a cached snapshot.

## Memory

The two `.ico` files stored all nine sizes as PNG, so `LoadImageW` decoded them
through WIC — and that one call brought `WindowsCodecs.dll` (2.3 MB of code
pages) into a tray process whose visible bitmaps are 16×16. The sizes this
program loads (16 through 48: every DPI a tray icon and a title bar ask for) are
now uncompressed DIB, where no decoder is involved. The large sizes stay PNG
because Explorer decodes those in its own process.

| | 1.0.3 | 1.0.4 |
|---|---|---|
| Private commit | 1912 KB | **1812 KB** |
| Working set | 11264 KB | **10384 KB** (−8%) |
| `WindowsCodecs` in module list | yes | **no** |
| Disk | 370 KiB | 411 KiB |

The pixels are identical and that is measured, not assumed: `icon_probe.exe`
loads the old and the new file, reads the bitmap back out of the `HICON` with
`GetDIBits`, and hashes it — both icons, both states, same hash.

The floor is the rest of the story: an empty Win32 message loop built with these
flags already commits **1584 KB**, so 87% of 1812 KB is the static CRT and the
DLLs the loader brings. The tray adds ~180 KB and the program's own data is
~36 KB. `msctf.dll` (1.4 MB) stays because a message-only window would stop
receiving the DPI and theme broadcasts; the report window's ~584 KB is the
Windows 11 compositor's UI stack. Neither is reachable from this code, and both
are documented with the number that proves it.

## Fixed

- The English report's "Clean residues…" button no longer clips its label. The
  three buttons were a fixed 118 px wide, which fits the CJK labels but not the
  English one; each is now measured from its own text in its own font.
- `--no-initial` was parsed and then overwritten by the persisted setting two
  statements later, so the flag had never skipped a sweep. It is run-scoped now:
  this run's start-up sweep is skipped, the stored setting and the menu tick are
  untouched.

## Tests and release tooling

- 13 gates, **369 assertions** across nine suites, all green on this exact
  source tree.
- New diagnostic tools, all reproducible from `docs/PERFORMANCE.md`:
  `bench_probes.cpp` (per-probe report cost), `bench_ua_match.cpp` (ROT13
  equivalence and four search strategies), `measure_mem.cpp` (commit by
  type/module/protect), `mem_floor.cpp` (the memory floor, layer by layer),
  `verify_handles.cpp` (300 passes of every reader, handle count flat),
  `verify_marks.cpp` (the maintained set against a fresh walk in seven states)
  and `icon_probe.cpp` (pixel hash across three loaders).
- `tests/test_robustness.py` pins the new contracts in source: one push
  function, one `NIM_MODIFY`, none when unchanged, no accounting after a failed
  push, one coalesced report refresh, copy without a rescan, menu count equal to
  report count, `PROP_MARK` with exactly one writer, reads that validate with
  `IsWindow` + `GetPropW` and never re-enumerate, the needle rotation, and both
  icon files keeping 16–48 as DIB with 256 still present.

## Verify before running

The binary is **unsigned**, so SmartScreen will warn on first run. The published
SHA-256 is the integrity check that replaces a signature:

```
477d3fb673049be1c96a01d4eb5f570e9a3eae49dc0644a6cb8d953a2d7b3ba1  ExplorerF11-1.0.4-win64.exe
```

`SHA256SUMS.txt` is attached. GNU `sha256sum` prescribes the line format
(`digest`, separator space, text/binary mode flag, filename), not the filename
of the manifest itself; `sha256sum -c SHA256SUMS.txt` works, and the digest is
paired with the asset name in the file content. On Windows:

```powershell
Get-FileHash .\ExplorerF11-1.0.4-win64.exe -Algorithm SHA256
(Get-Item .\ExplorerF11-1.0.4-win64.exe).VersionInfo.FileVersion   # 1.0.4.0
.\ExplorerF11-1.0.4-win64.exe --version                            # ExplorerF11 1.0.4
```

## Residue policy

The report lists only ExplorerF11's own registry and tray records. `--clean`
asks for confirmation and deletes those records and nothing else. The default
configuration writes nothing, and no optimisation in this release added a cache,
a file, or a registry value.
